# PrepAI Backend

This is the FastAPI backend for PrepAI — AI-Powered Mock Interview & Career Preparation Platform.

## Phase 1: Foundation (Completed)
- FastAPI setup
- MongoDB Atlas connection
- CORS configuration
- Basic Health endpoints

## Phase 2: Authentication (Completed)
- User registration and login flow using FastAPI OAuth2 `Bearer` scheme.
- Passwords are encrypted and verified using `bcrypt`.
- JWT token issuance (`PyJWT`) for protected routes.
- MongoDB `users` collection setup with a unique index on `email`.
- Protected endpoint: `GET /api/auth/me`.

> **Note**: Gemini, Voice AI (LiveKit), automated interview generation, and the frontend have not been implemented yet. They will follow in subsequent phases.

## Phase 3: Interview Management (Completed)
- Interview CRUD operations (Create, List, Get, Update, Delete).
- Lifecycle operations (Start, Complete) with strict state machine validation (`draft` -> `in_progress` -> `completed`).
- Question management (Add, List, Get, Delete) manually linked to interviews.
- Response management (Submit, List).
- Strict ownership enforcement across all endpoints to prevent data leakage.
- Validated via comprehensive `pytest` test suite (`tests/test_interviews.py`).

## Phase 4: Resume Management (Completed)
- Secure, authenticated file upload for PDF and DOCX files.
- File size validation (limit: 5 MB).
- Extraction and cleaning of text content from resumes (using `PyMuPDF` and `python-docx`).
- Storage of metadata and extracted text in MongoDB `resumes` collection.
- Strict ownership enforcement; users can only list, view, and delete their own resumes.
- Comprehensive API Endpoints:
  - `POST /api/resumes/upload`
  - `GET /api/resumes`
  - `GET /api/resumes/{resume_id}`
  - `DELETE /api/resumes/{resume_id}`
## Phase 5: Gemini AI Question Generation (Completed)
- Integration with Google Gemini (`gemini-2.5-flash`) via the `google-genai` SDK.
- Configurable environment variables for model and API key.
- Structural prompting to enforce JSON output using Pydantic schemas.
- Context-aware generation based on Role, Skills, Experience, Job Description, and linked Resume Text.
- Generates up to 20 questions securely, storing them with a `source = gemini` flag.
- **Note**: AI evaluation, adaptive interviewing, voice agents, and LangGraph are not implemented yet.

## Phase 6: Text Interview Engine (Completed)
- Full state-machine interview flow: `draft` → `in_progress` → `completed`.
- Interview state tracking via `current_question_id` and `current_question_number`.
- Contextual AI follow-up questions generated by Gemini after each primary answer.
- Maximum **1 follow-up per primary question** enforced to prevent infinite conversations.
- Graceful Gemini failure handling — falls back to the next primary question if AI errors.
- Duplicate answer prevention via unique compound index.
- Strict validation: only the current question can be answered, empty answers rejected.

**Architecture:**
```
User → Start Interview → Get Current Question → Submit Answer →
Follow-up Decision (Gemini) → Follow-up OR Next Primary →
Repeat → All Questions Answered → Interview Completed
```

**New Endpoints:**
- `POST /api/interviews/{id}/start` — Start interview, get first question.
- `GET /api/interviews/{id}/current-question` — Get the active question.
- `POST /api/interviews/{id}/questions/{qid}/response` — Submit answer to current question.
- `POST /api/interviews/{id}/next` — Advance to next question (may trigger AI follow-up).

> **Note**: AI evaluation and feedback are NOT implemented in Phase 6. They belong to Phase 7.

## Phase 7: AI Evaluation & Feedback Engine (Completed)

After an interview is completed, the candidate can trigger an AI evaluation powered by Google Gemini. The system analyzes all questions and answers and returns comprehensive structured feedback.

**Architecture:**
```
Completed Interview
    ↓
Questions + Answers
    ↓
Gemini Evaluator (app/ai/evaluator.py)
    ↓
Structured JSON
    ↓
Pydantic Validation (app/schemas/feedback.py)
    ↓
MongoDB (feedback collection)
    ↓
Feedback API Response
```

**Evaluation Output:**
- `overall_score` — 0–100 overall performance score
- `category_scores` — `technical`, `communication`, `problem_solving`, `relevance` (each 0–100)
- `question_evaluations` — per-question `score`, `quality`, `strengths`, `improvements`, `feedback`
- `strengths` — interview-wide strengths
- `weaknesses` — actionable weaknesses
- `recommendations` — practical improvement suggestions
- `topic_analysis` — per-topic `score` and `assessment` (Weak → Excellent)
- `summary` — concise overall performance summary

**Re-evaluation:** Calling `POST /evaluate` again replaces the existing feedback (one document per interview, upsert strategy).

**Unanswered questions** receive `score: 0` and `quality: "Not Answered"`.

**Context truncation limits** (to prevent token overflow):
- Resume text: max 3,000 characters
- Job description: max 1,000 characters
- Each individual answer: max 2,000 characters

**API Endpoints:**
- `POST /api/interviews/{id}/evaluate` — Trigger AI evaluation (interview must be `completed`)
- `GET /api/interviews/{id}/feedback` — Retrieve stored feedback

> **Note**: Analytics, voice interviews, and agentic AI are NOT implemented yet. They belong to Phase 8+.


## Phase 8: Analytics & Performance Tracking (Completed)

> **No LLM is used for analytics calculations.** All statistics are derived deterministically from MongoDB data generated by Phase 7.

Phase 8 adds a complete analytics backend that aggregates Phase 7 evaluation data into meaningful performance statistics.

**Architecture:**
```
Completed Interviews
        ↓
Feedback Collection (Phase 7 data)
        ↓
analytics_service.py
  └─ _get_enriched_feedback()  ← MongoDB $lookup join
        ↓
Aggregated Statistics
        ↓
Analytics APIs (12 endpoints)
```

### Score Definitions

| Metric | Definition |
|--------|-----------|
| `average_score` | Mean of `overall_score` across all evaluated interviews |
| `best_score` | Maximum `overall_score` |
| `lowest_score` | Minimum `overall_score` |
| `latest_score` | `overall_score` of most recently completed evaluated interview |
| `category_scores` | Average of each Phase 7 `category_scores` field across all interviews |
| `topic_analysis` | Average topic score from Phase 7 `topic_analysis` arrays |
| `strengths/weaknesses` | Frequency count of normalized (lowercase) text across all feedback |

### Improvement Calculation

Sorted chronological scores are split into two halves:
- **Earlier half** = `scores[:mid]`
- **Recent half** = `scores[mid:]`

| trend | condition |
|-------|----------|
| `improving` | `recent_avg − prev_avg ≥ 2` |
| `declining` | `prev_avg − recent_avg ≥ 2` |
| `stable` | `abs(difference) < 2` |
| `insufficient_data` | Fewer than 2 evaluated interviews |

### Date Filtering

All analytics endpoints (except `/improvement`) support optional `?days=N` filtering:
- Allowed values: `7`, `30`, `90`, `365`
- Omit for all-time history
- Invalid values return HTTP 400

### Analytics Endpoints

| Method | Endpoint | Description |
|--------|----------|-------------|
| `GET` | `/api/analytics` | Full dashboard payload |
| `GET` | `/api/analytics/overview` | Counts + score summary |
| `GET` | `/api/analytics/score-trend` | Chronological scores (oldest→newest) |
| `GET` | `/api/analytics/categories` | Average per evaluation category |
| `GET` | `/api/analytics/topics` | Topic performance (sort by score desc) |
| `GET` | `/api/analytics/strengths` | Recurring strengths by frequency |
| `GET` | `/api/analytics/weaknesses` | Recurring weaknesses by frequency |
| `GET` | `/api/analytics/history` | Paginated completed interview history |
| `GET` | `/api/analytics/interview-types` | Avg score by interview type |
| `GET` | `/api/analytics/difficulty` | Avg score by difficulty level |
| `GET` | `/api/analytics/roles` | Avg score by job role |
| `GET` | `/api/analytics/improvement` | Improvement trend analysis |

### Pagination

`GET /api/analytics/history` supports:
- `?page=N` (default: 1, min: 1)
- `?limit=N` (default: 10, min: 1, max: 50)

### Topic Limiting

`GET /api/analytics/topics` supports:
- `?limit=N` (default: 20, min: 1, max: 20)

### Empty States

If a user has no evaluated interviews:
- Counts return `0`
- Score fields return `null`
- Lists return `[]`
- Improvement returns `{ "trend": "insufficient_data" }`

### Security

- All endpoints require JWT Bearer token
- `user_id` is always derived from the authenticated token (never from request body/query)
- MongoDB queries always filter by `user_id` — users can never access another user's analytics

### MongoDB Indexes

| Collection | Index | Purpose |
|-----------|-------|---------|
| `interviews` | `user_id` | Filter by user |
| `interviews` | `created_at` | Sort/filter by date |
| `interviews` | `status` | Filter completed interviews (Phase 8) |
| `feedback` | `interview_id` (unique) | One feedback per interview |
| `feedback` | `user_id` | Filter by user |

## Phase 9: Voice Interview Engine (Completed)

Real-time voice interview mode powered by LiveKit and the Gemini Live API.

### Architecture

```
Candidate (browser/app)
       │  WebRTC audio
       ▼
  LiveKit Room
  ┌─────────────────┐
  │  Voice Agent    │ ← voice-agent/agent.py (separate process)
  │  (Gemini Live)  │ ← gemini-2.5-flash-native-audio-preview
  └────────┬────────┘
           │ HTTP (JWT)
           ▼
  PrepAI Backend ← this service
  MongoDB Atlas
```

### Voice Session Lifecycle

```
POST /api/interviews/{id}/voice/session  →  status: "created"  (token returned)
POST /api/interviews/{id}/voice/start    →  status: "active"   (interview begins)
[voice conversation via LiveKit]
POST /api/interviews/{id}/voice/end      →  status: "completed"
GET  /api/interviews/{id}/voice/transcript   → full conversation transcript
POST /api/interviews/{id}/evaluate           → Phase 7 AI evaluation (unchanged)
```

### New Endpoints (Phase 9)

| Method | Endpoint | Description |
|--------|----------|-------------|
| POST | `/api/interviews/{id}/voice/session` | Create LiveKit room + participant token |
| GET  | `/api/interviews/{id}/voice/session` | Get session status (no token) |
| POST | `/api/interviews/{id}/voice/start` | Start the voice interview |
| POST | `/api/interviews/{id}/voice/end` | End the voice interview |
| GET  | `/api/interviews/{id}/voice/transcript` | Retrieve conversation transcript |
| POST | `/api/interviews/{id}/voice/transcript/append` | Append transcript entry (agent use) |

### New MongoDB Collection

`voice_sessions` — stores session lifecycle, room name, and transcript entries.

### Environment Variables (add to backend `.env`)

```env
LIVEKIT_URL=wss://your-project.livekit.cloud
LIVEKIT_API_KEY=APIxxxxxxxxxxxxxxxx
LIVEKIT_API_SECRET=<secret — never commit>
```

Get these from [cloud.livekit.io](https://cloud.livekit.io) (free tier).

### Voice Agent

The voice agent runs as a **separate Python process** in `voice-agent/`.
See [`voice-agent/README.md`](../voice-agent/README.md) for full setup instructions.

### Security Model

- `LIVEKIT_API_SECRET` is used only server-side for token signing — never returned to client
- `GEMINI_API_KEY` is used only inside the voice agent process
- `user_id` is always derived from JWT — never accepted from request body
- LiveKit participant token grants minimal permissions (mic publish + subscribe only)
- Room name alone does NOT grant access — a signed token is always required

## Phase 10: Agentic AI with OpenRouter GPT-4o + LangGraph (Completed)

Introduces an **agentic AI architecture** that orchestrates existing PrepAI services using LangGraph and OpenRouter (GPT-4o).

> **Gemini remains unchanged** — it is still responsible for question generation, evaluation, follow-ups, and voice AI.
> **OpenRouter GPT-4o** is used exclusively for orchestration, career coaching, and tool-calling workflows.

---

### Architecture

```
User (natural language message)
        ↓
FastAPI  POST /api/agent/run
        ↓
agent_service.run_agent()
        ↓
LangGraph  StateGraph
        ↓
GPT-4o Orchestrator Node
   (determines intent via tool-calling loop)
        ↓  conditional routing
  ┌──────────────────────────────────┐
  │ question_node  │ interview_node  │
  │ evaluation_node│ analytics_node  │
  │      coach_node                  │
  └──────────────────────────────────┘
        ↓
Existing PrepAI Services (Gemini / MongoDB / Phase 5–8)
        ↓
GPT-4o (interprets results, forms response)
        ↓
AgentResponse { success, task, response, data }
```

### Security Architecture

| Threat | Mitigation |
|---|---|
| GPT-4o accessing MongoDB | All DB access via Python tool functions only |
| GPT-4o executing arbitrary code | Tool allowlist in `tool_calling.py`; no eval/exec |
| Cross-user data access | `user_id` always injected from JWT; never from LLM |
| Unknown tool injection | `execute_tool()` raises `UnknownToolError` for any unregistered name |
| API key exposure | Keys loaded from settings only; never logged or returned |
| Infinite tool loops | Maximum 5 tool-calling rounds per request |

---

### LangGraph Workflow

Nodes: `orchestrator_node → [question_node | interview_node | evaluation_node | analytics_node | coach_node] → END`

Valid routing actions (allowlist enforced in `app/graph/edges.py`):

- `conduct_interview`
- `evaluate_interview`
- `analyze_performance`
- `get_coaching`
